# 2026-10-14 链接播放验证

网络兼容修复现已作为 [0.3.4 Windows 开发版](https://github.com/FullPeople/MusicBoard/releases/tag/v0.3.4) 发布。下面保留调试过程中的成功与失败记录，最终包和公开更新结果见末段。

0.3.4 候选增加首次播放衔接：保留预载时的解码连接，首次播放接着读取其余音频，不重复连接。预载仍为 2 秒，其后最多缓存 8 个解码块；未播放的连接在 10 秒后关闭。定位、再次播放及独立音效继续拥有各自的解码任务。

独立服务在第三次及以后的媒体请求前延迟 3 秒，旧行为需要 6 次请求，实际播放停在 2 秒处。候选只需 4 次请求，同一延迟条件、同一观察窗口内实际位置达到 4.05 秒，原生检查通过。没有延长观察时间或降低播放位置要求。WAV、MP3 的原生检查还确认预载与后续音频逐采样匹配，并验证截断、取消与实际供音。

在线播放增加 HTTP 代理隧道协议支持，并与下载使用相同的请求身份。平台解析未提供 User-Agent 时，播放器采用相同的默认请求头；来源已有的 Referer 保留。原生在线播放自检增加失败原因，便于区分解析、连接和解码问题。

通过实际导入窗口下载后，再独立检查音频文件，B 站、YouTube、网易、QQ 音乐、SoundCloud 和 Bandcamp 的公开测试链接均成功。网易返回 30 秒试听，界面明确提示；这不证明整首歌曲可用。酷我、酷狗和 Vimeo 在该本地工具配置下未通过，仍需使用完整发行配置继续排查。

修复候选配合本地工具运行时，B 站和 YouTube 的实际在线播放均通过，包括原生按钮、预载、XAudio2 播放超过预载区、停止和无曲库文件写入。改用已逐项核对摘要的发行音频运行时及随包插件后，B 站、网易、QQ 音乐、SoundCloud 和 Bandcamp 各 9 项通过；YouTube 已准备成功，但该轮播放超过预载区的检查失败。失败证据保留，不能据前一轮成功宣称发行运行时全部通过。

`tools/verify_public_online_audio.py` 要求实际音频输出，出现音频设备跳过即失败。`tools/verify_online_proxy.py` 使用自有 HTTP 代理和 `.invalid` 目标，验证真实 WAV、MP3 解码及供音。旧候选和新候选的普通 HTTP 代理检查均通过；它不能复现 HTTPS 代理隧道问题，也不能当作该问题的修复证明。HTTPS 隧道拒绝已通过实际公开来源的解码错误确认，最终仍须核对完整发行环境。

测试音频、配置和日志保存在独立验证目录，没有使用真实曲库或浏览器登录信息。后续仍需完成 YouTube 预载后连续播放、更多来源、长期中断与地址过期、完整安装升级及官网发布。

后续源读取改为平台工具通过标准输出直接供给解码器，保持平台的请求头、分块和重试行为。这是 [yt-dlp 文档提供的流式播放接口](https://github.com/yt-dlp/yt-dlp/wiki/FAQ#how-do-i-stream-directly-to-media-player)。两个进程使用同一个自有 Job Object，分别只继承所需的输入输出管道，防止传输结束后仍因多余句柄而等待。首次预载连接复用及缓存上限保留。

接入后，同一发行音频运行时和插件下，YouTube、B 站、网易、QQ 音乐、SoundCloud、Bandcamp 六组共 54 项全部通过。这是指定公网样本的短时供音、停止和无曲库文件写入结果，不代表长期中断及所有歌曲验证完成。作者 WAV／MP3 各 16 项原生检查也通过，新增流式管道的逐采样一致性、传输失败后正确结束，以及同时取消传输与解码进程。

云端 Windows 构建机没有可用音频输出，因此云检查分别报告解码结果与设备跳过。`online_handoff_tests` 在相同延迟服务上验证预载、无需重连的后续解码及与本地参考音频逐采样一致；该检查不声称播放成功。严格的 `verify_online_handoff_delay.py` 默认模式仍要求 XAudio2 实际播放，音频设备跳过仍失败。本机延迟播放、32 项原生结果和 54 项公网结果独立保留，不能用无声卡云结果替代。
