## 波形包络：不用"猜"，用真 PCM

原版 `waveform_analyzer.gd` 对**压缩字节**做"能量分析"
（`_analyze_compressed_energy`）—— 它算的是字节偏离 128 的均方根，
和实际响度没有确定关系。那个文件在原型里最后根本没被用上（是死代码，
`main.gd` 里没有引用）。它的自述注释就写着"利用此特性提取**近似**波形"。

这里改成从真 PCM 算，两条设计：

1. **包络从"已经解出来准备播的 PCM"算，不单独再解一遍。**
   一首 4 分钟的歌是 42 MB 的 PCM16；为了画波形再解一次，
   等于把播放前的等待时间翻倍。`compute_waveform_envelope(const DecodedAudio&, ...)`
   就是为这条准备的。
2. **纯函数。** 收样本指针、帧数、声道数、桶数，返回每桶峰值。
   于是可以完全离线穷举：正弦、静音、单点尖峰、削顶、左右声道不一致、
   桶数多于帧数、−32768 的绝对值——全部不需要素材。

两条容易写错、专门钉住了的地方：

| 断言 | 为什么值得单独测 |
| --- | --- |
| 静音就是一条直线，**不伪造底噪** | 原版在分析失败时会 `_generate_silent_waveform()` 返回一条 0.02 的"底噪"——那是把"不知道"画成"看起来有声音" |
| 归一化按**全局峰值**，不是按满刻度 | 很多素材录得偏轻，按满刻度归一化之后波形会贴在中间一条线上，什么都看不出来 |

一条刻意的取舍写进了断言与注释：整段很轻、只有一个满刻度尖峰时，
归一化之后其余部分会显得很小 —— 那是**真实**的动态范围，不该被压平。
留着这条注释是为了免得以后被"顺手优化"掉。

## 封面提取：只读标签区域，不读整个文件

**这是这一层的核心纪律。** 为了一张封面把某个 20 MB 的文件整个读进内存，
和"扫描阶段就 decode"是同一类错误。所以：

| 容器 | 怎么读 | 在哪停 |
| --- | --- | --- |
| MP3 | 读 ID3v2 头的 10 字节 → 按它声明的长度读整段标签 | 标签区域上限 24 MB |
| FLAC | 从 "fLaC" 之后逐个读元数据块头（4 字节），跳过非 PICTURE 块 | PICTURE 块上限 = 封面上限 |
| Ogg Vorbis | 在前 2 MB 里找 `METADATA_BLOCK_PICTURE=` 再解 base64 | 搜索窗口上限 2 MB |
| MP4 / M4A | 递归找 atom（moov→udta→meta→ilst→covr） | 深度上限 8 层 |
| 同目录图 | 直接读，但有大小上限 | 16 MB |

实测：全库 491 个文件取一遍封面，**Release 1.06 秒**。

**Ogg 那一路是有意简化的。** 完整的 Ogg 解析要处理 27 字节页头、段表、
跨页拼包；而那个字段名只可能出现在注释头里，注释头总在文件最前面。
直接找字段名比实现页重组器简单得多，也不会因为一个畸形页而整条路失败。
代价是"注释头大到超出 2 MB 就找不到封面"——这是**有界的退化**，不是错误。
这条写在代码注释里，不藏。

**MP4 的 covr 顺手也做了**（虽然真实曲库里一个 m4a 都没有）：
递归 atom 搜索约 80 行，是机械活；而且 yt-dlp 换个参数就会产出 m4a，
那时候没封面会很难查。

### "没有封面"与"读不出来"必须分得开

这是本模块契约里写明的：

- 返回 `false` 且 `failure` **为空** → 这首歌就是没有封面。界面回退黑胶。
- 返回 `false` 且 `failure` 非空 → 读的过程中出了问题，原因要能上屏。

有两条用例专门断言这件事（"没有标签的 mp3" 与 "文件不存在"）。
分不开的后果是用户看到一句莫名其妙的错误，或者更糟 ——
一个坏标签让整首歌在界面上没有任何封面，而没人知道为什么。

### 测试抓出来的两个构造错误（都在测试自己身上）

1. **MP4 的 `ftyp` atom 写成了 `atom("ftypM4A ", ...)`。**
   atom 的 type 字段只有 4 字节；"M4A " 是 body 的头 4 字节（主品牌）。
   写错之后声明长度比实际长度小 4，解析器只能判定"尺寸不合理"然后放弃 ——
   **测试失败的表现是"没有封面"，而不是"格式错"**，这一点也在提示：
   解析器的"放弃"路径要不留痕迹地吞掉很多东西，所以每个分支都要有用例。
2. **未同步（unsynchronisation）的用例构造错了。**
   我先在图片里插了一个 0x00 却没改标签声明长度，于是解析器读到的是
   一个自称长度与实际不符的标签 —— 测的其实是"截断的标签"，不是未同步。
   正确顺序是：先按正常尺寸建好帧 → 再对整段做未同步 → 最后用**未同步之后**
   的长度写标签头。改对之后（用 JPEG，因为它天然含 0xFF）一次通过。

这两条都是"测试看起来在测一件事、实际在测另一件事"，
和前面几轮踩到的搜索串写错、坐标口径搞混是同一类。

## 真实曲库的封面分布

```
255 / 491 个文件有封面（52%），Release 1.06 秒 / Debug 3.92 秒
```

这个数字本身就是设计决策的依据：设计稿里"有封面时整盘显示封面，像光盘的印刷面"
不是锦上添花 —— 一半以上的曲目都会走到那条分支。
反过来说，如果这一层没做，界面上会有一半的唱片是"看起来是黑胶、其实只是没读封面"。

## 未完成 / 边界

- **内嵌封面的容器覆盖**：mp3 / flac / ogg / mp4 / wav 已做；
  wma 与 aiff 明确不做（返回"没有封面"，界面回退黑胶）。真实曲库里没有这两种。
- **同一文件里多张图**：只取第一张能解出来的。设计稿没有"选择封面"的入口，
  所以没有做优先级排序（比如按"图片类型 = 封面"优先）。
  真实文件里 APIC 通常只有一张。
- **封面解码成位图**（WIC）与超采样到唱片尺寸属于 UI 层，阶段 6b。
- **包络的桶数**目前是界面宽度的常量（320）。真正接上之后可能需要按控件宽度算，
  那时要看是不是值得缓存（一首歌 4 分钟的解码结果本来就常驻，
  再算一次 320 桶是微秒级，暂时不值当）。
