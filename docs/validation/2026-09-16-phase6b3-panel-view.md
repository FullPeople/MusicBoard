## 为什么用"预览模式"而不是先把正式程序接完

正式程序要做的事（消息循环、播放接线、拖放、快捷键分发）与"把画面画出来"
是两件独立的事。绘制是最难自动验证的一层 —— 它只能靠人看图；
而它也是我现在唯一还没给人看过的东西。

所以这一步先把绘制做完、用**真实素材**渲染一帧出来给人看，
而不是等整个程序接完才第一次看见界面。`--panel` 模式只做三件事：
扫曲库 → 填状态 → 画一帧存 PNG，不起消息循环。

## 渲染暴露出来的四个问题

这四个都是"看代码觉得没问题、画出来一眼就看见"的：

| 问题 | 根因 | 修法 |
| --- | --- | --- |
| 芯片行压在第一行卡片上 | `take_top` 已经吃掉了搜索框高度，代码里又加了一次 46px | 只再加"间距"；并补一条断言：芯片底 ≤ 网格顶 |
| 芯片行一路画到隔壁列上 | 21 个分类总宽远超一列，而绘制没有裁剪 | 按原型 `.chips{overflow-x:auto}` 的意思把这一行裁在容器里 |
| 芯片宽度是固定 70px | 布局层没有字体度量，只能估 | 用 `IDWriteTextLayout` 实测（按名字缓存），**绘制与命中区域共用同一份宽度** |
| 底栏右侧显示"搜索音乐…" | 底栏那行复用了搜索框的占位文字 | 给 `PanelState` 加 `library_label`，显示曲库路径 |

芯片宽度那一条不只是外观问题：**命中区域的矩形与看得见的区域本来会对不上** ——
固定 70px 的芯片画着 120px 宽的文字，用户点在药丸右半边不会命中。
这类"看着能用、点着不对"的错最难查，所以宽度必须在同一处算出来给两边共用。

底栏那一条值得单独说：那行代码单独看完全合理（"显示一句提示文字"），
只有把它渲染出来、看见底栏上冒出"搜索音乐…"，才知道拿错了字段。

## 两次"没有 HRESULT 的 abort"：D2D 资源是设备相关的

这一轮踩到了与阶段 3.5 同类的坑，两次，症状都是**直接 abort、没有任何错误信息**：

1. **封面位图**画到了截图用的软件 target 上。
   封面位图是用设备上下文建的，而 `save_frame_png` 走的是
   `CreateWicBitmapRenderTarget` —— 完全是另一张 target。D2D 直接 abort。
2. **画刷**也是。原来在 `initialize` 里用窗口的 target 建一把画刷就一直用，
   截图那条路换成了软件 target，于是同一把画刷被画到别的 target 上。

修法两条都写在代码里：

- `PanelView::target_supports_covers(target)`：只认建位图时那个设备上下文，
  别的一律跳过封面、回退黑胶。
- `ensure_brush(target)`：画刷按 target 缓存，target 变了就重建。

**规律是**："设备相关资源不能跨 target 用，违反了也没有 HRESULT"。
阶段 3.5 是几何与描边样式取自另一个工厂，这一轮是位图与画刷跨 target ——
同一条规则的两个面。在这两处都留了注释，因为下一次还会以第三种面目出现。

## 这一轮新增的资产

**`src/ui/panel_view.*`**：把 `PanelState` 按 `PanelLayout` 画出来。
它不决定任何行为 —— 状态怎么变、点了谁、拖到哪里全由调用方拿着 `HitMap` 决定。
这样切是为了让"行为"能脱离像素去测，而"绘制"能脱离行为去改。

几个与设计稿直接对应的实现细节：

| 设计稿要求 | 实现 |
| --- | --- |
| 音波图进度用**遮罩**，不是进度线 | 同一份波形画两遍：整条灰，再用 `PushAxisAlignedClip` 裁出已播段画成总线色 |
| 盘上不写字；有封面就整盘是封面 | 圆形裁切 + 按"填满"缩放居中，避免非正方封面被拉变形 |
| 中心圆点就是播放状态 | 灰 = 空闲/暂停，总线色 = 播放中；暂停时整体**往背景暗色混**（不是降 alpha） |
| 曲名过长用省略号 | `CreateEllipsisTrimmingSign` + `DWRITE_TRIMMING_GRANULARITY_CHARACTER`，由排版引擎决定在哪省 |
| 搜索框与悬停预览是同一个盒子 | 布局上输入框与预览区是同一个矩形的两段；名字在前、波形在后 |
| 音效台布局 `h{v{h{v{功能按钮},唱片},音波图},音量条}` | 左侧竖向双按钮、中间唱片+音波图、右侧竖向音量条 |

**`src/app/panel_preview.*`**：从真实曲库填一个能画的 `PanelState`。
它会把 BGM 台填成"正在播放 42% 处"、第一张卡填成播放中、第三张填成已选中、
第二张填成被悬停（于是悬停预览里有真名字与真波形），
音效台里两台"在响"、四台各带一个快捷键角标 —— 一次渲染把各种状态都看到。

## 未完成（下一步）

正式程序（`panel_main`）还没写。它要做的是：

1. 消息循环（定时器 ~60fps）→ 每帧 `engine.update` → 需要时重画；
2. 用 `HitMap` 把布局矩形登记成命中区域，接上悬停 / 点击 / 拖动 / 滚轮；
3. 播放接线：卡片拖到唱片 → `AudioEngine::play`；点唱片 → 暂停/继续（保持位置）；
   点/拖音波图 → seek；滚轮 → `ScrollState`；
4. `WM_HOTKEY` → 触发对应音效台；
5. 搜索框的文本输入（Win32 的字符输入与退格）；
6. 从资源管理器拖文件进来 → 导入事务（`import_staged_file`）。

这些的每一块依赖都已经就位且被测过，所以剩下的是接线与交互，
不是新的基础设施。**注意**：正式程序一旦有了消息循环，
"点击是否命中"这类问题就变成可交互验证的，而不再只是布局断言。

## 仍然未验证的

- **真人在桌面上操作的手感**：拖动跟不跟手、悬停切换是否闪烁、60fps 稳不稳。
  本机能出的证据只有静态帧。
- **125%/150%/200% 缩放下这一帧长什么样**（本机只有一块 100% 的屏）。
  阶段 3.5 补上的 `SetTransform` 让缩放路径在代码上成立，
  但"150% 下布局好不好看"只能靠人眼。
- 面板上的封面：预览这一帧里没有封面显示，因为**封面位图不能画到截图那张
  软件 target 上**（见上）。屏幕上是有封面的 —— 这一点目前只有代码保证，
  没有像素证据。要出带封面的证据，得把 `save_frame_png` 改成
  "在设备上下文上画到位图再读回"，那是一件独立的小事。
