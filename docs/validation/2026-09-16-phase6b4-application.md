## 一句话结论

`musicboard.exe` 能跑了：读设置 → 扫曲库（473 首 / 20 分类 / 3.2 秒）
→ 建面板与悬浮球 → 接音频引擎 → 注册全局快捷键 → 建通知区域图标 → 消息循环。

**交互自检 37/37 通过**（后来加到 65/65），Debug 与 Release 都是。
自检用**真实的事件处理函数**驱动主要交互 —— 这是这一层唯一没有覆盖的部分：
布局有几何断言、绘制有像素证据，而"点了到底有没有反应"只能靠人点。

## 结构

`Application` 只负责"谁在什么时候被调用"与"状态怎么变"：
交互全部由 `HitMap` 决定（命中区域来自 `PanelLayout`），绘制全部由 `PanelView` 做。

面板窗口派生成 `PanelWindow : public CompositionWindow` 来处理自己的消息 ——
消息处理本来就是窗口的派生行为，用回调会让消息路径变成一次隐式间接调用。
为此把 `CompositionWindow` 的 `final` 去掉了（这是这一阶段对平台层唯一的改动）。

消息循环用 `SetTimer(hwnd, 16ms)` + `WM_TIMER`，不自己写循环 ——
这样 `TransparentWindow::run_message_loop` 不用动。

## 自检抓到的两个真问题

### 1. 拖不到空唱片上

唱片的命中区域被注册成 `enabled = state.bgm.has_track` —— 因为"空盘上不该有反应"。
但唱片**同时是拖放的落点**，于是"拖到空盘上开始播"这个最主要的交互完全失效。

"空盘上点击没有反应"应该由动作里的 `in_use` 判断保证（`toggle_bgm_pause` 已经
这么做了），**不该用禁用命中区域去实现** —— 那会把拖放一起禁掉。

### 2. 淡入期间界面不认为在播放

引擎的 `slot_state().playing` 要求 `current_gain > 0`，而淡入是从 0 开始的 ——
于是拖上去之后整整 1.2 秒里盘面不转、点唱片也不像暂停。

对界面来说，"请求了播放且没暂停"就是播放中；音量大小由电平表单独表达。
改成 `deck.playing = deck.has_track && !slot.paused`，口径写在代码注释里。

## 测试自身的两处问题

1. **退格走了不存在的入口**：真机按退格会**同时**产生 `WM_KEYDOWN(VK_BACK)` 与
   `WM_CHAR('\b')`，而程序只在 `WM_CHAR` 里处理（两边都处理会一次删两个字符）。
   自检里用 `on_key_down(VK_BACK)` 测的是另一条不存在的路。
2. **断言用了引擎的口径而不是界面的口径**：断言 `slot.playing` 为真，
   而界面按"在台上且没暂停"显示 —— 于是得出"界面错了"的错误结论。
   断言要跟着界面的口径走，并另加一条"淡入真的在爬升"把两个口径都钉住。

## 顺带接上的

- `default_settings_path()` / `product_data_root()`：`%LOCALAPPDATA%\MusicBoard`。
  取不到环境变量时返回**空路径**由调用方明确失败，不静默落到当前目录 ——
  那会变成一个"设置怎么丢了"的谜。
- 启动时清理七天前的旧导入暂存目录（`prune_staging` 之前写好了却没人调）。
  导入失败会故意留证据，但证据不该永久留着。

## 未验证的部分

- **真人在桌面上操作的手感**：拖动跟不跟手、悬停切换闪不闪、60fps 稳不稳。
  自检只能证明"接线通了、状态对了"。
- **面板上的封面**：屏幕上应该有（封面缓存 54 条测试、`target_supports_covers`
  的规则在），但静态帧里看不到 —— 见阶段 6b 第三步记录里那条说明。
- **125%/150%/200% 缩放下的观感**（本机只有一块 100% 的屏）。
- **长时间运行的稳定性**：没跑过几小时。已知一处可优化的地方：
  每帧重画都会重建合成表面（`resize_composition_surface`），
  播放时是每秒 60 次 4 MB 级的分配合释放。要不要改成"只在进度变化超过一个像素时
  重画"或复用表面，等真实使用里看有没有问题再定。
