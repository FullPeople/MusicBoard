# 验收记录 · 原型对齐第四轮（用户逐条反馈）

日期：2026-09-17
范围：用户列出的 12 条问题。其中三条查出来是**真 bug**，而且一条比一条严重 ——
它们的表现互相重叠，所以放在最前面说清。

## 三条真 bug（用户看到的现象都归它们）

### 1. 换曲之后进度是错的（"大部分音波图错误的显示进度或保持满进度"）

播放位置的算法是：

```
position = (SamplesPlayed − samples_played_at_seek) / 采样率 + seek_offset_seconds
```

而 `play()` **从来没重置过这两个字段** —— 它们只在 `seek()` 里被写过。
于是一旦这一路上 seek 过（或放过别的曲子），下一首的位置就从上一次的残留开始算；
残留比新曲时长还大时，进度直接显示成满的。
再加上 `SamplesPlayed` 是声部**一生**的累计值（Flush 不清零），
同一路里放的每一首都会受影响 —— 这正好解释了"大部分音波图"。

修法：`play()` 在 Start 之后重新读一次基线，并把 `seek_offset_seconds` 归零。

### 2. 大量音乐永远卡在"正在载入"（"大量音乐没办法播放"）

后台音频任务的去重集合与队列**不同步**：新请求会把队列清空只留最新一个，
但被丢掉的那些 key 还留在"已排队"集合里 —— 于是它们再也不会被排队、
结果也永远不会出现，界面永远停在"正在载入"。

修法：丢掉排队任务时一并摘掉"已排队"标记；界面侧再加一道自愈（拿不到就重新请求）。
自检里加了回归：连续请求三个音频（中间顶掉一个），被顶掉的那个**必须还能拿到**。

### 3. 清空/换曲之后音波图不重置（"清空按钮不一定能清空音波图等"）

`state_` 是常驻成员，而 deck 的填充只在 `if (has_track)` 分支里赋值 ——
曲子放完、被清空、正在切换时，那些字段保持上一首的值：波形、时长、路径都还在。

修法：每帧**先清空再填**（`deck = ui::DeckView{}`），把"上一帧的残留"这条路封死。

## 启动预热（"做一个导入"）

启动后在**后台**把整库过一遍：逐首解码、算出包络、记下解不开的文件。
好处：悬停任何一张卡都是现成的波形；每个文件被读过一遍，系统文件缓存热了，
之后起播的解码明显快；解不开的文件会被数出来并报在日志里。

关键是**它不能挡交互**。队列因此分三级：

```
urgent_（悬停 / 起播要的）  →  audio_（一次只留最新一个）  →  warmup_（整库预热）
```

491 首排在一个 FIFO 里的话，用户悬停要排在几百个任务后面 —— 那就等于把
上一轮修好的悬停延迟又调回来。所以交互请求不仅优先，还会把**已在预热队列里的
同一个 key 提上来**。

进度显示在**底栏的曲库标签**上，不占状态胶囊：胶囊是给用户动作反馈的
（"正在播放 X"），被后台进度顶掉的话用户会以为刚才那次拖放没生效。
（这条是我自己造的回归，改完才发现。）
